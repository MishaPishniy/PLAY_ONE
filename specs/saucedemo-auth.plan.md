# SauceDemo — план перевірки авторизації

Дата дослідження: 2026-10-09, Europe/Kiev.
URL: https://www.saucedemo.com/.
Інструкції: `.github/agents/playwright-test-planner.agent.md`.
Seed: `tests/seed.spec.ts` (порожній каркас).
Наявний автотест: `tests/saucedemo.spec.ts` (успішний вхід standard_user).

## Обсяг і метод

Перевірено інтерфейс входу, помилки, доступ дозволених і заблокованого користувачів, збереження сесії, вихід та захист внутрішніх маршрутів. Це функціональна перевірка браузерного інтерфейсу, а не аудит серверної безпеки чи ролей.

Дослідження виконано через підключений Playwright: кожний незалежний приклад запускався в новому BrowserContext. Спеціальні інструменти `planner_setup_page` і `planner_save_plan` у сесії недоступні; план збережено безпосередньо у Markdown. Нові автотести в межах планування не створювалися.

Статус «Перевірено» означає, що описану поведінку спостерігали під час дослідження; це не результат запуску майбутнього автоматизованого набору. Очікування нижче зафіксовано за поточною поведінкою сайту, оскільки окремої продуктової специфікації не надано.

## Передумови для кожного сценарію

- Починати з нового контексту браузера без cookies, localStorage та збереженої авторизації. Кожний рядок параметризованої таблиці — окремий незалежний тест.
- Відкрити `https://www.saucedemo.com/`, якщо сценарій не вказує інший початковий маршрут.
- Для сценаріїв після входу виконати вхід усередині цього самого тесту; не залежати від попередніх тестів.
- Тестовий пароль усіх опублікованих на сайті користувачів: `secret_sauce`.
- Успішний вхід: URL точно `https://www.saucedemo.com/inventory.html`, видимий Products і `[data-test="inventory-list"]`, кнопка Login прихована.
- Відмова у вході: URL `https://www.saucedemo.com/`, видима форма Login і потрібне повідомлення; каталог не відображається.
- Кожний критерій перевіряти після завершення переходу та очікування потрібного елемента. Не читати URL одразу після Back без очікування редиректу.

## Сценарії

### AUTH-01. Успішний вхід дозволеного користувача — P0

Статус: **Перевірено** для всіх п'яти рядків. Початковий стан: новий контекст, Login.

| Username | Password |
| --- | --- |
| standard_user | secret_sauce |
| problem_user | secret_sauce |
| performance_glitch_user | secret_sauce |
| error_user | secret_sauce |
| visual_user | secret_sauce |

1. Заповнити Username і Password даними одного рядка.
2. Натиснути Login.
3. Дочекатися сторінки каталогу.

Очікування / успіх: виконуються всі загальні критерії успішного входу; title сторінки — Swag Labs.
Провал: помилка входу, інший URL або каталог не з'являється в межах тайм-ауту.
Примітка: для `performance_glitch_user` спостерігалося близько 5,2 с від натискання до каталогу. Це спостереження, не вимога до швидкодії. Візуальні та товарні особливості спеціальних користувачів поза обсягом цього сценарію.

### AUTH-02. Вхід клавішею Enter у полі Password — P1

Статус: **Перевірено**. Початковий стан: новий контекст, Login.

1. Ввести `standard_user` і `secret_sauce`.
2. Залишити фокус у Password і натиснути Enter.
3. Дочекатися каталогу.

Успіх: ті самі критерії, що для AUTH-01, без натискання кнопки мишею.
Провал: форма не відправляється або вхід не виконується.

### AUTH-03. Вхід лише з клавіатури — P1

Статус: **Перевірено**. Початковий стан: нова сторінка Login без попередніх кліків.

1. Натиснути Tab: фокус переходить у Username; ввести `standard_user`.
2. Натиснути Tab: фокус переходить у Password; ввести `secret_sauce`.
3. Натиснути Tab: фокус переходить на Login.
4. Натиснути Enter.

Успіх: порядок фокусу Username → Password → Login, потім успішний вхід.
Провал: елемент недоступний із клавіатури, порядок інший або вхід не виконується.

### AUTH-04. Обов'язкові поля — P0

Статус: **Перевірено**. Початковий стан: новий контекст, Login для кожного рядка.

| Username | Password | Точне очікуване повідомлення |
| --- | --- | --- |
| порожньо | порожньо | Epic sadface: Username is required |
| порожньо | secret_sauce | Epic sadface: Username is required |
| standard_user | порожньо | Epic sadface: Password is required |

1. Заповнити лише непорожні поля відповідно до рядка.
2. Натиснути Login.
3. Перевірити повідомлення й відсутність доступу до каталогу.

Успіх: відмова у вході з точним повідомленням із таблиці.
Провал: вхід дозволено, помилки немає або вказано інше обов'язкове поле.

### AUTH-05. Неправильні облікові дані — P0

Статус: **Перевірено**. Початковий стан: новий контекст, Login для кожного рядка.

| Username | Password |
| --- | --- |
| standard_user | wrong_password |
| unknown_user | secret_sauce |

1. Ввести дані одного рядка.
2. Натиснути Login.
3. Перевірити стан форми й повідомлення.

Успіх: відмова з `Epic sadface: Username and password do not match any user in this service`.
Провал: доступ дозволено, повідомлення відсутнє або не відповідає очікуванню.

### AUTH-06. Заблокований користувач — P0

Статус: **Перевірено**. Початковий стан: новий контекст, Login.

1. Ввести `locked_out_user` і `secret_sauce`.
2. Натиснути Login.

Успіх: відмова з `Epic sadface: Sorry, this user has been locked out.`.
Провал: відкривається каталог або немає очікуваного повідомлення.

### AUTH-07. Пробіли й регістр — P1

Статус: **Перевірено**. Початковий стан: новий контекст, Login для кожного рядка. Пробіли всередині кодових фрагментів є частиною введення.

| Username | Password |
| --- | --- |
| ` standard_user ` | `secret_sauce` |
| `standard_user` | ` secret_sauce ` |
| `STANDARD_USER` | `secret_sauce` |
| `standard_user` | `SECRET_SAUCE` |
| три пробіли | три пробіли |

1. Ввести дані, зберігши регістр і пробіли.
2. Натиснути Login.

Успіх: кожний варіант відхилено з повідомленням із AUTH-05; пробіли не обрізаються до валідних даних.
Провал: вхід успішний або повідомлення відрізняється від зафіксованої поведінки.

### AUTH-08. Виправлення пароля після помилки — P1

Статус: **Перевірено**. Початковий стан: новий контекст, Login.

1. Ввести `standard_user` і `wrong_password`, натиснути Login.
2. Дочекатися повідомлення із AUTH-05.
3. Не закриваючи повідомлення, замінити пароль на `secret_sauce`.
4. Натиснути Login.

Успіх: повторна спроба відкриває каталог; попередня помилка не блокує форму.
Провал: коректні дані відхиляються або форма перестає працювати.

### AUTH-09. Закриття повідомлення про помилку — P1

Статус: **Перевірено**. Початковий стан: новий контекст, Login.

1. Ввести `standard_user` і `wrong_password`, натиснути Login.
2. Дочекатися alert і натиснути Dismiss error.
3. Перевірити, що alert прибрано, а значення обох полів збережено.
4. Замінити пароль на `secret_sauce`, натиснути Login.

Успіх: повідомлення зникає, дані не очищаються, повторний вхід успішний.
Провал: повідомлення залишається, поля несподівано очищаються або повторний вхід неможливий.

### AUTH-10. Сесія після оновлення та в новій вкладці — P0

Статус: **Перевірено**. Початковий стан: новий контекст, Login; обидві вкладки належать цьому контексту.

1. Увійти як `standard_user` із `secret_sauce`.
2. Оновити сторінку inventory.html.
3. Перевірити видимість каталогу й URL.
4. Відкрити нову вкладку того самого контексту за адресою `/inventory.html`.
5. Перевірити видимість каталогу й URL у другій вкладці.

Успіх: обидва переходи зберігають доступ без повторного входу.
Провал: валідна сесія втрачається після reload або не діє в іншій вкладці.

### AUTH-11. Прямий доступ без авторизації — P0

Статус: **Перевірено** для шести маршрутів. Початковий стан: новий порожній контекст для кожного маршруту, без попереднього входу.

| Маршрут для відкриття | Шлях у повідомленні |
| --- | --- |
| /inventory.html | /inventory.html |
| /cart.html | /cart.html |
| /checkout-step-one.html | /checkout-step-one.html |
| /checkout-step-two.html | /checkout-step-two.html |
| /checkout-complete.html | /checkout-complete.html |
| /inventory-item.html?id=4 | /inventory-item.html |

1. Відкрити повну адресу SauceDemo з маршрутом одного рядка.
2. Дочекатися редиректу на `/` і появи Login.
3. Перевірити повідомлення `Epic sadface: You can only access '<шлях>' when you are logged in.`.

Успіх: користувач залишається поза захищеною сторінкою, відображається Login і потрібне повідомлення.
Провал: захищений вміст доступний без входу або редирект/повідомлення некоректні.

### AUTH-12. Logout і повторний прямий доступ — P0

Статус: **Перевірено**. Початковий стан: новий контекст, Login.

1. Увійти як `standard_user` із `secret_sauce`.
2. Натиснути Open Menu → Logout.
3. Дочекатися `/`; перевірити Login та порожні Username і Password.
4. Відкрити `/inventory.html` напряму.
5. Дочекатися редиректу й перевірити помилку з AUTH-11 для inventory.html.

Успіх: вихід повертає на порожню форму, прямий доступ до каталогу відхиляється.
Провал: сесія продовжує давати доступ або форма зберігає введений пароль після виходу.

### AUTH-13. Кнопка Back після Logout — P0

Статус: **Перевірено**, включно з повторним спостереженням після очікування редиректу. Початковий стан: новий контекст, Login.

1. Увійти як `standard_user` із `secret_sauce`.
2. Вийти через Open Menu → Logout і дочекатися `/`.
3. Натиснути Back у браузері.
4. Дочекатися завершення переходу й редиректу на `/`.

Успіх: видима форма Login, каталог прихований, повідомлення відповідає AUTH-11 для inventory.html.
Провал: після завершення переходу користувач знову має доступ до каталогу.
Примітка: відразу після Back URL може короткочасно бути inventory.html; це не підтверджує відновлення доступу.

### AUTH-14. Вихід впливає на іншу вкладку — P0

Статус: **Перевірено**. Початковий стан: новий контекст, Login.

1. Увійти як `standard_user` із `secret_sauce` у вкладці A.
2. Відкрити `/inventory.html` у вкладці B того самого контексту.
3. У вкладці A виконати Open Menu → Logout.
4. Оновити вкладку B.

Успіх: B перенаправлено на Login з повідомленням із AUTH-11 для inventory.html.
Провал: після оновлення B каталог залишається доступним.
Межа перевірки: миттєве приховування вже відображених товарів у B без оновлення не перевірялося й не є критерієм цього сценарію.

### AUTH-15. Маскування пароля — P1

Статус: **Частково перевірено**: підтверджено `type="password"`; візуальне маскування та перевірка до відправлення заплановані. Початковий стан: новий контекст, Login.

1. Ввести `wrong_password` у Password.
2. Перевірити, що поле має тип password і візуально показує масковані символи.
3. Ввести `standard_user`, натиснути Login.
4. Після помилки повторно перевірити тип поля та маскування.

Успіх: поле не показує пароль відкритим текстом до й після помилки.
Провал: пароль відображається відкрито або тип поля змінюється на text.

### AUTH-16. Довгі значення та відновлення форми — P2

Статус: **Заплановано, не виконувалося**. Початковий стан: новий контекст, Login для кожного варіанта.

Варіанти: Username = 256 символів `a`, Password = `secret_sauce`; Username = `standard_user`, Password = 256 символів `a`.

1. Ввести дані одного варіанта, натиснути Login.
2. Перевірити відмову, відсутність каталогу та працездатність форми.
3. Замінити дані на `standard_user` / `secret_sauce` й повторити вхід.

Очікування / успіх: некоректні дані не надають доступ, форма залишається працездатною, коректна повторна спроба успішна.
Провал: обхід входу, зависання або неможливість повторної спроби.
Припущення: 256 — обране тестове значення, не заявлена максимальна довжина. Точне повідомлення або обмеження довжини потрібно уточнити під час виконання.

## Результати дослідження

- Для AUTH-01–AUTH-14 спостережувана поведінка відповідає описаним критеріям; відтворюваних функціональних дефектів у цих перевірках не знайдено.
- AUTH-15 має часткове покриття; AUTH-16 ще не виконувався.
- Спеціальний `performance_glitch_user` входить із помітною затримкою; без погодженого SLA це не класифікується як новий дефект.
- Не перевірялися Firefox/WebKit, мобільні viewport, тривале закінчення сесії, робота офлайн, серверна авторизація та захист від атак.

## Рекомендації для генератора Playwright

1. Зберегти глобальну конфігурацію QAuto. Для файлу SauceDemo перевизначити baseURL, використати порожній storageState й не успадковувати облікові дані QAuto.
2. Використовувати `getByRole('textbox', { name: 'Username', exact: true })`, аналогічно Password, та `getByRole('button', { name: 'Login', exact: true })`.
3. Підтверджені локатори: `[data-test="title"]`, `[data-test="inventory-list"]`, `[data-test="error"]`; кнопки Open Menu, Logout, Dismiss error доступні за role/name.
4. Для авторизації не перевіряти ціни, сортування чи точну кількість товарів. Вони не визначають успішність входу.
5. Параметризувати таблиці, але кожний рядок оформити окремим тестом. Для перевірок вкладок використовувати один контекст лише всередині відповідного тесту.
6. Використовувати web-first assertions і очікування URL; не додавати фіксовані sleeps. Дати сценарію `performance_glitch_user` достатній timeout для відомої затримки, наприклад 15 с на очікування каталогу.
7. Не додавати `test.only`. Спочатку автоматизувати P0, потім P1/P2. Усі сценарії мають запускатися незалежно та в довільному порядку.
